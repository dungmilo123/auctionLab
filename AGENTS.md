## Project: AuctionLab

Current implementation follows `manage-vintage-lots-and-auction-events`: PostgreSQL 18 replaces runtime SQLite for both the retained game and the independent commerce catalog. The change's explicit PostgreSQL decision supersedes the former SQLite/no-external-database constraint. `add-bidder-accounts-and-watchlists` adds commerce identities, digest-only fixed-lifetime sessions and private watchlists through additive migration 2. Timed bidding uses migration 3; winner orders and local simulated payments use additive migration 4; order history/fulfillment/demo reset use migration 5; private interactions/coverage use migration 6.

- Go 1.26, `net/http`, gorilla/websocket v1.5.3, pgx/v5 v5.11.0 through `database/sql`; React/Vite/TypeScript. No CGO; frontend-first embedded binary. PostgreSQL is separately provisioned and required offline too.
- Required `DATABASE_URL`; validated dedicated `DATABASE_SCHEMA`, default `auctionlab`. Reject runtime `DB_PATH`. See `docs/postgresql.md` for app/test roles, health, ownership, and local setup.
- `modernc.org/sqlite` is limited to the explicit read-only offline v4 source importer. No live fallback, dual writes, automatic import, or conversion of legacy game amounts.
- Preserve game correctness: commit before publish; monotonic revisions; nonblocking enqueue in the engine lock; wall-clock crash recovery; role projections exclude truth values and sealed bids. One writer process per schema, using a dedicated leased connection. Do not reacquire ownership for stale memory.
- The catalog is separate from game items/budgets. USD integer cents use `*_minor`; publication is atomic and immutable. Publication does not start auctions, create bids/winners/orders, or mutate game revisions.
- Real PostgreSQL fixtures require `TEST_DATABASE_URL` and disposable owned schemas. Never touch operational schemas or the existing SQLite source for tests. Required DB tests fail clearly when the test service is missing.
- Admin document gate retains the capability cookie. Every private catalog API independently checks it. Keep secrets out of frontend code and reports. Public catalog DTOs explicitly exclude private notes, versions, keys and game secrets.
- Account registration/login/profile and published-lot watchlists use independent commerce sessions. Commerce bidding and private winner checkout with simulated payment are implemented. Owner-only order history, capability-authorized administration, simulated fulfillment and explicitly bounded demo reset are implemented. Private aggregate analytics and deterministic rule-based recommendations are available; trained ML remains out of scope. Sold closure commits its owned order atomically; startup adopts historical winners before HTTP readiness. Account roles never replace the catalog capability. Do not mount the retained game UI or create game sockets from the website.
- Demo accounts are provisioned only by stopped-writer `--seed-accounts` or explicitly scoped `--prepare-demo`/`--reset-demo` maintenance with operator-supplied password environment inputs. Normal startup installs no credentials. Keep migrations 1–5 immutable; health reports the supported schema version (currently 6). Checkout contact/receipt data stays owner-private; confirmation success requires a confirmed atomic commit and one receipt per order.

Active operator documentation is in `README.md`, `docs/postgresql.md`, and `web/README.md`. `PROJECT.md` and `PLAN.md` referenced by the earlier generated guidance are absent from this checkout; do not recreate their historical content or alter archived evidence.
